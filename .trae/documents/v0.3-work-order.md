### 各项要点与验收

**#1 词形变化**（2026-10-10 用户四轮澄清后的最终口径：搜 dying 出相邻两条——①dying 独立词条（音标+释义首行，点击进 dying 详情）；②dying 变形标注条（同词名，无音标无释义，第二行灰色小字「die 的现在分词」，点击进 **die** 详情））
- 搜索页：`SearchViewModel` 对 `search()` 每条结果用 `DictRepository.parseExchange(entry.exchange)` 判断：含 `0:lemma` 且 lemma≠自身 → 正常条后紧随追加变形标注条（`SearchWordResult.inflectionHint` / `clickTarget=lemma`）；搜原型词不带出变形词；原型不在词库时变形条照出（标注来自 exchange 字段，不依赖原型词条存在）
- 详情页：「词形变化」栏（原型行 + 「本词是 die 的现在分词」说明 + 各变形列表）保留显示但**全部取消点击改纯文本**；「变形」栏（inflections 反向家族列表）**整段删除**（`DictRepository.inflectionsOf()` 一并移除）；「派生」栏每行加点击跳转 `onOpenWord(derived.term)`，视觉不变
- 保留：`parseExchange` / `EXCHANGE_LABELS` / `exchangeInfo()`
- 验收：单测（exchange 解析）+ 双端构建 + Watch4 真机查 dying/better（双条相邻、标注正确、分别进 dying/die 详情）

**#2 短语（方案 A）**
- `tools/build_phrases.py`：下载初中/高考/CET4/CET6/考研书 → 提取 `phrase.phrases{pContent,pCn}` → 清洗（去测度词残缺条目如 "a basin of"、`(army) general` 括号形态可选保留）→ 去重 → 在 `ecdict_core.db` 新建 `phrase(phrase TEXT PK, zh TEXT, src_word TEXT)` 表 → `DICT_VERSION = 2`
- 预计 6-8 万条、体积 +3MB 左右；构建后检查 db 体积，超 15MB 需与用户商量裁剪
- `DictRepository` 加 `searchPhrases(query)`（phrase/zh 双向 LIKE）+ `relatedPhrases(term)`（按 src_word 查）
- **不新加页面**：短语与单词混合呈现在现有搜索结果流里，短语加「词组」标识；搜索历史无需改动（term 直接存）
- 详情页**最底部**新增「关联短语」栏；**长按**短语条目跳转到该短语的释义展示（phrase 表条目详情）
- 首次启动迁移：DICT_VERSION 升级触发 assets 重拷贝（已启动过的用户覆盖旧 db）
- 验收：构建脚本可重跑、搜短语在现有搜索页直接出结果、详情页底部关联栏长按可跳、版权声明三处到位、双端真机验证

## 5. 离线翻译：用户调研结论（2026-10-10）与 A 路线预研计划

**用户调研结论：只做 A 路线（Marian int8 ONNX 现成权重），先校准量具，再决定是否开 B/C。**

| 路线 | 磁盘/内存/延迟 | 可动手性 |
|------|---------------|---------|
| **A. Marian int8 ONNX**（Xenova/opus-mt-en-zh，encoder 50.3MiB + decoder-merged 57.2MiB + 词表 ~1.6MB ≈ 112.7MB/单语向；fp32 基线 298MB） | 峰值内存估 150-250MB；单句延迟估 1-4s（双 A55 待实测） | **今天就能动手**，权重现成 |
| B. MobileNMT 式自蒸馏（15MB/30ms 论文口径） | 需拿 Hy-MT2-1.8B（Apache-2.0）当 teacher 造伪标注，训 20-40M 参数模型 | ✗ 无开源权重/数据集，数周 + GPU 训练机，仅当 A 不达标再开 |
| C. 极低比特混合精度 + DMBL（11.8x 体积 / 8.3x 内存 / 3.5x 速度，BLEU -0.5） | 无开源实现，要自己写量化器/kernel | ✗ 仅作为 A 装不下时的后备补丁 |

- 推理引擎：ONNX Runtime Mobile（int8 QDQ，ARM dot-product 通路）。CTranslate2 是 x86 服务器向，ARM Android 生产路径未核实，**不走**；MNN（有 0.5B 级量化模型）可作备选试手感
- **A 唯一技术风险点：ORT Mobile 能否顺畅吃下 encoder-decoder + 贪心/beam 解码，需实测一次**
- 量具校准三件事（纸面算不准，必须跑）：
  1. `getMemoryClass()`/`getLargeMemoryClass()` 在 Watch4 上实测返回值 + `adb shell dumpsys meminfo` 看系统剩余
  2. 冷加载 112.7MB 权重到第一次出词的耗时（flash 读取时间可能比推理还长）
  3. 10 条日常句子的译文延迟 + 峰值 RSS + 后盖温度 + 掉电
- 量具 2、3 决定是否开 B/C

### 引擎双选方案（用户 2026-10-10 追加：加入 Google ML Kit 供用户选择）

| | 引擎 1：Marian int8 ONNX（A 路线，主推） | 引擎 2：Google ML Kit translate 17.0.3 |
|---|---|---|
| 模型体积 | 112.7MB/单语向（en→zh） | ~30MB/语言对 |
| 质量 | 日常短句够用，优于 ML Kit | 垫底（模型小） |
| 速度 | 待实测（估 1-4s） | 快（亚秒级） |
| 模型获取 | **自主可控**：GitHub Release 附件分发（同 APK 渠道），支持配置镜像 URL（ghproxy 类加速），应用内下载 | **只能走官方下载器**（Google 服务器，URL 写死在 SDK）；无公开镜像/本地注入方案（社区 dump 注入 hack 依赖内部路径，脆弱不可靠，已排除）。国内用户需一次可访问 Google 的网络完成下载，之后离线可用 |
| 内存 | 估 150-250MB 峰值 | 低（~50MB 级） |

- **无可靠办法跳过 Google 下载 ML Kit 模型**——官方无本地模型加载 API（translate 不像 AutoML Vision 支持 bundle/本地源）。ML Kit 的卖点只剩「轻量快」，国内首次下载是它的固有短板，产品上如实标注
- **调研新发现：华为 HMS ML Kit 也有离线翻译**（54 语种，MLLocalModelManager，模型走华为服务器国内可达，API 与 Google 版几乎同构）——国内无 GMS 设备的潜在第三选项；但需 AGC 项目注册/鉴权配置 + 又一套 SDK 体积，**暂不集成，仅记录**
- 双引擎都进量具校准 demo：**同一批 10 句测两引擎的延迟/峰值 RSS/译文质量对比**，数据出来再定默认引擎与 UI 呈现；量具校准工时由半天调为 1 天
- 引擎选择 UI：设置里做「翻译引擎」选择项（智能/快速两档或直接列引擎名），仅对达标设备显示
- APK 代价叠加：ORT ~+12MB，ML Kit translate + 几 MB，合计 APK 预计 ~28MB（模型均不进 APK）

### 工程补充判断（AI 2026-10-10）

1. **先只做 en→zh 单语向**：背单词场景以英→中为主；zh→en 再加 112MB 且双倍常驻内存，等 en→zh 量具达标再说
2. **设备门槛现实**：150-250MB 常驻在 Watch4（RAM 1.5GB）是贴极限跑；华强北安卓 9（RAM 512MB-1GB）基本出局——翻译功能必须按 `memoryClass` 实测值动态降级（不达标设备隐藏入口），不能全局默认开
3. **不做语音链路**：ASR 再加几十 MB 不划算，先用文本输入 + 系统语音键盘
4. **产品形态待定**：整句翻译入口（独立页 vs 详情页例句翻译按钮）等量具数据出来再定，不提前做 UI
5. 排期建议：**量具校准作为独立小项插在 #4 之后**（1 天，独立调试 demo 同时接两引擎对比测，不动主功能）；是否继续做完整翻译功能由量具数据 + 用户拍板
