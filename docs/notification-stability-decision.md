# 后台通知稳定性方案评估与决策依据

## 问题

应用后台被系统清理（force-stop / 省电清理 / Doze）后，每日背单词提醒不再准点推送。

## 候选方案评估

| 维度 | 方案A：开机自启常驻后台插件 | 方案B：接入系统级推送服务 | 方案C：退出仅保留通知组件 | 方案D：行业惯例组合拳 |
|---|---|---|---|---|
| 资源占用 | 高：常驻进程/前台服务持续吃内存 | 低：无常驻组件 | 中：仍需一个存活组件 | 极低：零常驻组件 |
| 电量消耗 | 高，手表上尤其敏感 | 低 | 中 | 极低 |
| 系统兼容性 | 差：Wear OS 对后台自启管控严格（无自启白名单入口），国产表带阉割更狠 | 差： Wear OS 无法接入 FCM 之外的服务；独立手表应用接 FCM 需 Google 服务，国行表不可用 | 中：前台服务在 Wear OS 3+ 有系统限制，表盘旁常驻图标打扰用户 | 好：全部使用系统标准机制 |
| 实现复杂度 | 高（前台服务+保活拉活，失败率高） | 高（需配手机端/账号体系） | 中 | 低（纯系统 API） |
| 用户体验 | 差：常驻通知栏图标、发热 | 好（但依赖不可用的基础设施） | 中：多一个常驻图标 | 好：无感知 |
| 判定 | 否决：投入大、失败率高、体验差 | 否决：独立手表 App 无可用推送通道 | 否决：过度设计，牺牲体验换非必要可靠性 | **采纳** |

## 决策：方案D —— 精确闹钟 + 多时机重排 + 电池白名单（行业标准做法）

闹钟类应用（系统时钟、AnkiDroid、各种喝水提醒）的通用做法，零常驻组件：

1. **精确闹钟**（`setExactAndAllowWhileIdle`）：即使设备进入 Doze 深睡眠也能准点唤醒。
   - API 33+（Wear OS 4+）声明 `USE_EXACT_ALARM` 即自动授予，无需用户操作；
   - API 31-32 走 `SCHEDULE_EXACT_ALARM`（该年代默认授予）；
   - 权限被收走的极端情况下退化为 10 分钟窗口的 `setWindow`，保证"至少送到"。
2. **一次性闹钟 + 发完自排**：精确闹钟没有每日重复版，`ReminderReceiver` 发完通知后
   立刻把明天的排上，不依赖进程存活。
3. **四重兜底重排**（闹钟因 force-stop / 重启 / 覆盖安装丢失时补排）：
   - `BootReceiver`：开机完成（原有）+ 覆盖安装 `MY_PACKAGE_REPLACED` + 改时间 `TIME_SET` + 改时区 `TIMEZONE_CHANGED`；
   - `VocabApplication.onCreate`：每次冷启动补排（覆盖手动划掉应用后重进的场景）；
   - 设置页每次修改提醒时间即时重排（原有）。
4. **电池优化白名单**：开启提醒时引导一次 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，
   防止厂商省电策略推迟闹钟；已在白名单则不打扰。

## 资源与体验影响

- 无常驻进程、无前台服务、无常驻通知：内存/电量影响可忽略；
- 所有机制均为系统标准 API，各厂商 Wear OS 兼容性最好；
- 用户侧唯一感知是开启提醒时的一次性系统弹窗。

## 局限说明

- 用户从最近任务里**手动划掉**（force-stop）后，所有闹钟在该次开机周期内失效，
  这是 Android 平台对 force-stop 的统一语义（系统时钟应用同样如此），
  只能靠下次打开应用时冷启动重排弥补；
- 国行表若搭载激进的厂商省电策略，白名单引导 + 精确闹钟已是最优可行解。
